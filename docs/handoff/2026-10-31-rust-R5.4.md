# R5.4: `hs-karaoke` JoinClient + RoomHost

วันที่ 31 ตุลาคม 2026 · branch `Sorryham` (ต่อจาก R5.3 `d8d08a0`) · commit ใน branch เท่านั้น ยังไม่ push · ทำโดย Sorryham (Claude Opus 5.5) รีวิวโดย Opus ตัวใหม่ตาม PLAN 10.4 แล้ว แก้ข้อพบครบ · อ่านสรุปรวมก่อนที่ [READ-ME-FIRST](2026-10-31-Sorryham-READ-ME-FIRST.md)

## สถานะ

| ไฟล์ Rust | ต้นทาง C++ | สรุป |
|---|---|---|
| `src/join.rs` | `JoinClient.{h,cpp}` | `join_client(rate, max_block) -> (JoinClient, JoinAudio)`. เธรด network เดียวถือ WebSocket (`tungstenite` บน TCP หรือ `rustls` + cert ของ Windows), `hs_net::rtc::RtcPeer`, Opus enc/dec, `FriendEcho`; คุยกับ audio thread ผ่าน ring ของ `hs-bus` 2 ตัว (ขึ้น/ลง) เหมือน C++. ขาลงเข้า `hs_engine::FriendReader` (jitter buffer). ขาขึ้น Opus HRA3 5 ms + FEC หรือ PCM HRA2 10 ms ถ้า Hub เก่า. resolve ลิงก์ถาวรผ่าน `hs_app::get_json`. reconnect ทุก 3 s, offline รอ 4 s |
| `src/room.rs` | `RoomHost.{h,cpp}` | `RoomHost::start(name, rate, max_block) -> Option<(RoomHost, RoomAudio)>`, ไม่มีห้อง = `mix_local`. เปิด bus `Main` (หรือ `Karaoke` ถ้า Hub ของ DAW ถืออยู่), claim hub, beacon, ShareServer ของ `hs-net` + ลิงก์เพื่อน 8 ช่อง, FriendReader ต่อเพื่อน, บันทึก WAV float ผ่าน ring + เธรดเขียนไฟล์ |
| `hs-bus/src/protocol.rs` | — | `ChannelRing::boxed()` ring ศูนย์บน heap (ให้ `hs-karaoke` ไม่ต้องมี `unsafe`) |

dependency ใหม่: `tungstenite 0.27` (handshake เท่านั้น เพิ่ม crate เล็ก 5 ตัว: sha1, digest, block-buffer, utf-8, tungstenite) · `rustls` / `rustls-platform-verifier` ใช้เวอร์ชันเดียวกับ `hs-app` (มีใน lockfile แล้ว). ไม่แตะ shm layout, wire, parameter ID, state format

## บั๊ก C++ ที่แก้ใน Rust

RoomHost (6):
1. **เพื่อนได้ยินเพื่อนผิดคน / ได้ยินเสียงตัวเองย้อน**: `friendVoiceAudio` ทุกคู่ได้ buffer เดียวกัน (เพื่อนคนสุดท้ายที่ pull หรือค่าค้าง). Rust: เพื่อน `j` แบบ mono ลงคู่ `j/2` ช่อง `j%2` เหมือน Hub (test ตรวจทั้ง 4 คู่)
2. block ที่ยาวกว่า `prepare` **เขียนเกิน scratch buffer** (memory corruption). Rust: ทำทีละช่วง
3. `stopRoom` unmap bus ขณะ audio thread ยังเขียน. Rust: ครึ่ง audio ถือ `Arc` ไว้ แค่หยุดเขียน
4. `startRoom` **memset bus ทั้งก้อน** ลบ slot ของ Track ที่อยู่บน bus เดียวกัน. Rust: ตั้งเฉพาะ header / friend ที่ใช้ (รวมล้าง `hubFlags`, `delayBits` = -1, ตำแหน่ง `friendVoiceWrite` = `friendMixWrite` ที่ memset เคยทำให้)
5. `kickSlot` reset jitter buffer จาก UI thread ขณะ audio thread ใช้อยู่. Rust: ตั้งธง audio thread reset เอง
6. หยุดอัดเสียงใช้ atomics แบบ relaxed (writer อาจถูกลบกลางการเขียน). Rust: SeqCst ทั้งสองฝั่ง และเธรดเขียนไฟล์รอบล็อกสุดท้ายเสร็จก่อนปิด

JoinClient (6):
1. **packet ที่มาช้า / ซ้ำ** (DataChannel ไม่เรียงลำดับ) ถูกเล่นผิดที่และทำให้ seq ถอย ตามด้วย PLC สูงสุด 10 บล็อก = เสียงกระตุก. Rust: ทิ้งด้วย `seq_gap` และ packet ก่อนช่องว่างกู้จาก FEC ของ packet ถัดไป (แก้แบบเดียวกับ Hub ใน 1.0.8) test `late_and_repeated_packets_are_dropped_and_a_gap_is_filled`
2. `disconnect` reset jitter buffer จาก UI thread. Rust: audio thread reset เอง
3. `setState` ใช้ `callAsync([this])` = use-after-free ถ้าลบ client ก่อน. Rust: UI อ่าน `state()` / `room_info()` บน timer
4. decoder / codec / seq ถูกใช้จาก 2 เธรด (WebSocket + callback ของ DataChannel) และ `roomInfo` อ่านโดยไม่ล็อก. Rust: เธรดเดียวถือ
5. ทุก packet ที่รับ alloc `std::vector`. Rust: buffer ถอดรหัส / reference สร้างครั้งเดียวต่อการเชื่อมต่อ (library WebSocket / DataChannel ยัง alloc ต่อข้อความ นอก audio thread เหมือนเดิม)
6. ลิงก์ `hearaside://join?url=` (ที่ RoomHost แจก) ใช้ได้แค่ผ่านหน้าต่าง `connect` ไม่เข้าใจ. Rust: รับทั้ง `has://join?u=` และ `hearaside://join?url=`

แก้หลังรีวิว: (1) **timeout 1 ms ตั้งบน socket ที่ `try_clone` มา ซึ่งบน Windows ไม่มีผลกับ socket จริง** ทำให้ `read` บล็อกได้ถึง 2 s → DataChannel ขึ้นช้า 6–7 s และเสียงออกเป็นก้อน. ตอนนี้ socket เป็น non-blocking และ loop พัก 1 ms เฉพาะตอนไม่มีงาน (`std::thread::sleep` บน Windows ใช้ timer ความละเอียดสูง ไม่ใช่ tick 15.6 ms) test ใหม่บังคับ DataChannel ขึ้นภายใน 3 s (ได้ ~2 s); (2) DNS (host ของ Hub, STUN) ทำบนเธรดทิ้งได้ จำกัด 4 s ให้ `disconnect()` ไม่ค้างตาม resolver, RtcPeer ได้ IP ของ STUN ไม่ทำ DNS เอง (แบบเดียวกับ ShareServer); (3) `pull_downstream` ที่ใหญ่กว่า `max_block` ทำทีละช่วง

## ต่างจาก C++ โดยตั้งใจ

1. สถานะ / ข้อมูลห้อง: UI อ่านด้วย `state()` / `room_info()` แทน callback
2. `RoomHost::start` คืน `None` ถ้า bus เปิดไม่ได้ (C++ ถอยไปใช้ bus บน heap ที่ OBS มองไม่เห็น) หรือ HAS Karaoke อีกตัว host อยู่บน bus นั้น
3. `RoomAudio::process` รับ vocal / music เป็นคู่ L R เสมอ (ไม่มีเสียงร้อง = ส่ง slice ศูนย์) แทน pointer ที่เป็น null ได้
4. `timelineCounter_` ของ C++ นับแต่ไม่เคยเขียนลง bus: ไม่ได้ port
5. ไม่มี proxy สำหรับ WebSocket (WinHTTP ใช้ proxy ของระบบ); `/api/resolve` ผ่าน client ของ `hs-app` ซึ่งใช้ proxy

## ยังไม่ได้ทำ / ให้ ArmZ ตัดสิน

1. **WASAPI** (R5.2 ย้ายมา R5.4): ไม่ได้ทำ ต้องมีตัวจัดการ device + audio callback ของแอปก่อน ซึ่งอยู่ใน R5.5 เสนอทำคู่ R5.5 หรือแยก R5.4b
2. **เป้า ไมค์ → หูฟัง ≤ 10 ms ที่ ASIO 128** (เกณฑ์เสร็จของ R5.4 ใน PLAN): วัดได้เมื่อแอปรันเสียงจริง (R5.5) ตอนนี้ยืนยันได้แค่ว่าชิ้นที่อยู่บน path นี้ไม่ alloc / ไม่ lock / ไม่เพิ่ม buffer (`rt_safety`)
3. ยังไม่ได้ลองกับ Hub จริงผ่านอินเทอร์เน็ต / wss (`trycloudflare` / ลิงก์ถาวร) / Hub C++ 1.0.10 (ทดสอบกับ ShareServer ของ Rust บน loopback เท่านั้น) และไม่ได้ลองโหมด PCM HRA2 กับ Hub 1.0.4 จริง
4. ยังไม่ได้ลอง OBS อ่าน bus ของห้อง (bus `Main` / `Karaoke`) จริง
