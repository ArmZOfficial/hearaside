## UDP loss/reorder (2026-10-31, continued)

`tests/web-friend/netsim-udp-compare.mjs` sends WebRTC DataChannel audio (`audio`, unordered, maxRetransmits 0) through a UDP proxy that drops and reorders packets.

1. **C++ cannot be the baseline.** With the pure C++ exe, Chrome never connects directly: ICE goes `checking` then `closed`, 0 packets (`-cpp-rtc-direct.log`, `-udp-smoke5.log`). This is a C++ WebRTC limitation on this machine, not a relay result. So no C++ vs Rust UDP comparison exists.
2. **Rust stress run (Rust on both arms, `--cpp` = Rust exe), 20 s, seed 7** (`-udp-rust-self-20s.log`): clean 0 / 0 gaps/min, proxy dropped 0. Bad profile: ~357 drops, ~8000 reorders; 943.3 vs 906.7 gaps/min, Opus decoded, no WebSocket fallback. The labels `cpp/` in that log mean "arm A", not C++.
3. This shows Rust UDP survives real loss/reorder. It is not proof of "no worse than C++".

R3.7 stays open: mobile/PCM TCP gap difference is uninvestigated, and the UDP criterion has no C++ baseline. Next: decide with ArmZ whether to accept the Rust stress result as the UDP evidence, or fix C++ direct WebRTC first; then look at the mobile/PCM traces.

**Decision (ArmZ, 2026-10-31):** the Rust UDP stress run is accepted as R3.7's UDP evidence. The only thing left before R3.7 can close is the mobile/PCM TCP gap difference, plus a review.

Script: count frames, `pos` skips and arrival gaps inside the 2–20 s window of each `build/R3.7-tcp-traces/mobile_pcm_*.json`.

| Trace | Packets | Frames/s delivered | pos skips (frames) | Arrivals >30 ms apart | Max gap ms |

| rust#2 | 1549 | 23964 | 8 (127744) | 16 | 499 |

1. The mobile cap carries only ~24k of the 48k frames/s PCM stream, so both sides are saturated and both drop audio at the same points (same number of `pos` skips).
2. Rust delivers slightly more audio per second and has fewer long arrival gaps (16/16 vs 25/19). Its silence fraction was already lower.
3. The +5 gaps/min (3 extra events in 36 s) comes from how packet timing falls against the fixed 10 ms threshold when the link is saturated. No metric shows Rust sending less or later.

Conclusion: the mobile/PCM gap-count difference is noise under a saturated link, not a Rust regression. Still needs the separate review before R3.7 is marked done.

## Review and close (2026-10-31)

A fresh Opus reviewer re-ran the playout model on the traces: same gap counts, and all trace hashes match. With matched seeds Rust is +4 (seed 7) and -1 (seed 8). C++ alone varies by 9 between its runs, and lateness and starve time are equal or better for Rust. The harnesses are sound, with no blocking issues. Note: the harness's strict mean rule reported FAIL (exit 1) for mobile/PCM; the cell is accepted as noise from the matched-seed analysis, not as a strict pass. The Hub stream position also advances only ~11.3 s per 18 s window on both sides under mobile/PCM, so saturation includes the Hub side, not only the link. **R3.7 closed.** Limits: n=2 runs; no C++ UDP baseline (accepted); no Safari, phone or real-internet test.
