# R5.2 — `hs-win::asio` (HAS Direct เป็น Rust)

วันที่ 31 ตุลาคม 2026 · branch `rs/R5.2-asio` (แตกจาก `70a6bee`) · commit ใน branch เท่านั้น ไม่ push · ยังไม่ผ่านรีวิว Opus ตาม PLAN 10.4 (ตารางสถานะ 0.4 ไม่ได้แก้)

## สถานะ

port ครบ `apps/karaoke/HasAsio.{h,cpp}` (467 + 28 บรรทัด) เป็น crate ใหม่ `rust/crates/hs-win` (module `asio`): อ่านรายชื่อไดรเวอร์จาก `HKLM\SOFTWARE\ASIO`, สร้างไดรเวอร์ด้วย `CoCreateInstance` (ใช้ CLSID เป็น IID เหมือน C++), เรียกผ่าน vtable ที่นิยามเอง (IUnknown + 21 เมธอด ตามลำดับใน C++), แปลง sample type 9 แบบ, รัน buffer switch บนเธรดของไดรเวอร์. **ไม่มี ASIO SDK ของ Steinberg และไม่ใช้ `cpal`**: dependency ใหม่ตัวเดียวคือ `windows-sys 0.61.2` ที่มีใน lockfile อยู่แล้ว (feature `Win32_System_Com`, `Win32_System_Registry`, `Win32_UI_Input_KeyboardAndMouse`)

พิสูจน์ด้วย: (1) golden ที่ได้จาก **C++ จริง** (คอมไพล์ `HasAsio.cpp` เดิมด้วย MSVC ใส่ header ปลอมแทน JUCE) ตรงทุกบิตทั้ง 9 sample type ทั้งสองทิศ, (2) ไดรเวอร์ปลอมที่สร้างจาก vtable เดียวกัน รันครบ lazy load → open → buffer switch → reset → close, (3) ไดรเวอร์ ASIO จริงบนเครื่องนี้ 3 ตัว (ดูหัวข้อ "ไดรเวอร์จริง")

## ที่ไม่ได้ทำ: WASAPI ผ่าน `cpal`

งานใน PLAN ระบุ "+ WASAPI ผ่าน cpal" แต่คำสั่งให้ทำเมื่อ C++ มีชั้น device ที่ตรงกัน `HasAsio.cpp` ไม่มี WASAPI เลย (WASAPI / DirectSound ของ HAS Karaoke มาจาก JUCE `AudioDeviceManager`) จึงไม่มีโค้ดให้ port และ `cpal` จะดึง dependency ทั้งต้นไม้ (ต้องตรวจ `cargo deny` ใหม่) โดยไม่มีใครใช้ ให้ทำตอน R5.4/R5.5 ที่สร้าง audio device manager ฝั่ง Rust (`hs-win::asio::DeviceType` เสียบเป็นอีก device type ข้างๆ ได้โดยไม่ต้องแก้)

## ความแตกต่างจาก C++ (ตั้งใจ) และบั๊ก C++ ที่แก้

1. **บั๊ก: NaN ออกเป็น full-scale ลบ**. `fmin(fmax(NaN, -1), 1)` ได้ -1 ใน C++ (fmax คืนค่าที่ไม่ใช่ NaN) ปลั๊กอินที่พ่น NaN ทำให้ interface ได้ค่า -1.0 ทุก sample = เสียงดังกระชากที่หูฟัง. Rust: NaN → 0 ทุก sample type (test `nan_is_silence_not_full_scale_negative`). ที่เหลือ (inf → ±1, -0.0 ฯลฯ) ตรงกับ C++ ใน golden
2. **บั๊ก: ปิด device ขณะ callback ยังรันอยู่**. C++ `close()` เรียก `disposeBuffers()` แล้วค่อยเคลียร์ `gActive` ถ้า buffer switch ยังอยู่กลางทาง จะอ่าน/เขียน buffer ที่ไดรเวอร์เพิ่งคืน และ destructor ของ `Device` อาจทำให้ callback ใช้ `this` ที่ถูกลบ (use-after-free). Rust: ตั้ง `open=false` → `stop()` ของไดรเวอร์ → เคลียร์ `ACTIVE` แล้วรอจน callback ที่ค้างอยู่ (นับด้วย `IN_FLIGHT`, SeqCst ทั้งสองฝั่ง) ออกหมด **แล้วค่อย** `disposeBuffers()` (test `closing_waits_for_a_buffer_switch_that_is_running`)
3. **ไม่มี lock ใน audio thread**. C++ ถือ `juce::CriticalSection` รอบ callback (ผิดข้อ 1 ของ Hard rules). Rust: audio thread แค่ *ลอง* จับ `busy` (atomic) ถ้า `start`/`stop` ถืออยู่ ก็เล่นเงียบบล็อกนั้นแล้วไปต่อ (wait-free); เธรดควบคุม spin รอได้นานสุดหนึ่ง callback
4. **ล้าง output ก่อนเรียก callback ทุกบล็อก**. C++ ปล่อยค่าบล็อกก่อนหน้าไว้ถ้า callback ไม่เขียนช่องนั้น (เสียงซ้ำ). Rust ล้างเป็น 0 ก่อน (memset ไม่ alloc)
5. **panic ใน callback ถูกจับ** (`catch_unwind` ในทุก `extern "system"`): device เงียบ, `Device::faulted()` เป็น true จนกว่าจะ `start` ใหม่. C++ ถ้า exception หลุดออก callback ของไดรเวอร์ = crash
6. **reset request**: C++ ใช้ `MessageManager::callAsync` (ไม่มีใน Rust) เปลี่ยนเป็นธง atomic + `Device::poll_restart()` ให้เจ้าของ device เรียกจากเธรด UI/timer; ทำงานเหมือนเดิม (stop callback → close → open ด้วยค่าเลือกเดิม rate 0 → start callback เดิม). ถ้า R5.5 ใช้ timer ต้องเรียก `poll_restart` ทุก ~100 ms
7. `start(cb)` ตอนมี callback เดิมอยู่แล้ว: Rust เรียก `stopped()` ของตัวเก่าก่อน (C++ ทิ้งตัวเก่าโดยไม่แจ้ง)
8. ไม่พอร์ต `getDefaultDeviceIndex` (= -1 เสมอ), `hasSeparateInputsAndOutputs` (= false), `getIndexOfDevice`: เป็นเรื่องของ JUCE device type ผู้เรียก Rust ไม่ต้องใช้. `DeviceType::create_device(name)` รับชื่อเดียว (C++ รับ out/in แล้วเลือกตัวที่ไม่ว่าง)
9. โหลดไดรเวอร์แล้ว `init` ล้ม: Rust เรียก `Release` ทันที และไม่โหลดซ้ำ (เหมือน C++ ที่ `loaded_` เป็น true แล้ว)

คงไว้เหมือน C++ โดยเจตนา: scale ขาออกคือ `fs-1` แต่ขาเข้าคือ `fs` (ไม่สมมาตร 1 LSB), อ่านเฉพาะ hive 64 บิต (`KEY_READ` ไม่ใส่ `WOW64_32KEY`), ไม่เรียก `CoUninitialize`, รายการ buffer size จำกัด 32 (เลขยกกำลัง 2) / 64 (ทีละ granularity) ช่อง, ไดรเวอร์ทำงานได้ครั้งละตัวเดียวทั้งโปรเซส (callback ของ ASIO ไม่มี context)

## สิ่งที่ ArmZ ต้องทดสอบด้วยมือ (hardware)

1. **interface อีกยี่ห้อหนึ่ง** ที่มีไดรเวอร์ ASIO ของผู้ผลิตเอง (เช่น Focusrite, MOTU, RME, PreSonus, Behringer, Audient, Universal Audio): `cd rust; $env:HS_ASIO_LOAD="<ชื่อใน HKLM\SOFTWARE\ASIO>"; $env:HS_ASIO_RUN="1"; cargo test -p hs-win --release --test installed -- --ignored --nocapture load_named` ดูว่า: ชื่อช่องถูก, rate/buffer ถูก, จำนวน buffer switch ใน 2 วินาที ≈ ค่าที่คาด, `bit_depth` ตรงกับที่ผู้ผลิตบอก (Int24LSB / Int32LSB ฯลฯ ลอง interface ที่ใช้ 24 บิตแพ็ก), gap ไม่เกิน 1.5 เท่าของความยาว buffer
2. **เสียงจริงสองทาง**: ต่อ HAS Karaoke (หลัง R5.4 เสียบ `DeviceType` เข้า) แล้วฟังไมค์ → หูฟัง ที่ buffer 128 @ 48 kHz ต้อง ≤ 10 ms (เป้า PLAN-karaoke-exe หัวข้อ 1, วัดด้วย loopback) ฟังหาเสียงแตก/คลิกตอน start, stop, เปลี่ยน buffer
3. **เปลี่ยนค่าในแผงควบคุมไดรเวอร์ขณะเล่น** (buffer size / sample rate): ไดรเวอร์ส่ง reset → `poll_restart()` ต้องเปิดใหม่ด้วยค่าที่เลือกและเสียงกลับมาเอง
4. **ถอด USB ขณะเล่น** แล้วเสียบกลับ: ต้องไม่ crash/ค้าง (เจ้าของ device เห็นผ่าน `poll_restart`/`open` ล้ม)
5. **เปิดค้างโดยโปรแกรมอื่น** (DAW จอง interface อยู่): `open` ต้องคืน error ที่อ่านรู้เรื่อง ไม่ค้าง
6. ไดรเวอร์ 32 บิตเท่านั้น (บางตัวลงใน `WOW6432Node\ASIO`) จะไม่อยู่ในรายการ: เหมือน C++ (hive 64 บิต) ตั้งใจไว้ ยืนยันว่ายอมรับ
7. ไดรเวอร์ห่อที่ถามเลือกอุปกรณ์ตอนโหลด (ASIO4ALL): ตรวจว่า dialog ขึ้นเฉพาะตอนผู้ใช้เลือก (`DeviceType::scan` ไม่โหลดไดรเวอร์ใดเลย)

## ที่ข้าม / ยังไม่ได้ตรวจ

1. WASAPI / `cpal`: ไม่ทำ (ดูหัวข้อด้านบน) เป็นของ R5.4/R5.5
2. **ไม่ได้รัน test บน Linux จริง** (WSL ที่มีไม่มี Rust): ตรวจแค่ `clippy --all-targets --target x86_64-unknown-linux-gnu` ผ่าน (compile ได้) CI `rust.yml` บน ubuntu จะรันครั้งแรกตอน push. จุดที่เสี่ยง: `extern "system"` = C ABI บน Linux ซึ่งไดรเวอร์ปลอมกับ host ใช้ชนิดเดียวกัน จึงไม่น่าต่าง
3. ยังไม่ได้เทียบ **ทั้ง `Device`** กับ C++ (ต้อง build JUCE + `hearaside_karaoke_test` ซึ่งไม่ได้ build ไว้ในเครื่องนี้และไม่มี test `Device` ใน C++ เลย): เทียบเฉพาะการแปลง sample (golden) ส่วน logic ของ `Device` ตรวจจากการอ่านโค้ดทีละฟังก์ชัน + ไดรเวอร์ปลอม + ไดรเวอร์จริง 3 ตัว
4. ยังไม่ได้ทดสอบ 2 สิ่งที่ฝั่ง C++ มี: `showControlPanel` กับไดรเวอร์จริง (test ปลอมตรวจแค่ว่าเรียก `controlPanel`), และ `GetActiveWindow` เป็น parent ของ dialog (ใน test ไม่มีหน้าต่าง = 0)
5. `miri` ไม่ได้รัน (CI รันเฉพาะ `hs-bus`); `unsafe` ของ crate นี้: vtable (`call!` ที่เดียว), `process` (สร้าง slice จาก buffer ไดรเวอร์ + เข้าถึง `UnsafeCell` ด้วยกฎ `open`/`busy`), `swap_callback`, registry/COM ใน `win.rs`
6. ลองได้เฉพาะ x86_64: ABI เป็นแบบ 64 บิต (`compile_error!` ถ้า build Windows 32 บิต เหมือน `static_assert` ใน C++)
7. worktree นี้ไม่มี `external/*` จึงทำ junction ไป `Hearaside plugin\external\*` เพื่อ build workspace (ไม่ได้ commit)
8. PLAN: ตาราง 0.4 ไม่ได้แก้. หัวข้อ 8 ข้อ 5 ระบุ `hs-win` ใช้ `unsafe` ได้อยู่แล้ว จึงไม่ต้องแก้แผน. แถว R5.2 ในหัวข้อ 6 ควรเขียนใหม่ให้ตรงกับที่ทำ (ตัด "WASAPI ผ่าน cpal" ไป R5.4)
