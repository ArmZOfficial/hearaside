# Rust migration compatibility fixtures

`fixtures/shm-v14-layout.json` records the shared-memory ABI from
`libs/ssbus/include/ssbus/protocol.h` at commit
`7f4eccc298734d78667b67fa51ee81dee41d0e2b` (version 1.0.10, protocol 14).
It was captured on Windows x64 with MSVC 19.44.35229.0. The fixture contains
27 constants, 12 enum groups, and sizes, alignments and all 157 field offsets
across 16 structs. Field alignment is the declared member type's natural
alignment; explicit `alignas` placement is captured by its offset.

This is a **source ABI fixture**, not a dump from a released plug-in binary.
VST class IDs, parameter IDs and state blobs from shipping 1.0.10 binaries live
under `fixtures/plugins-1.0.10`. DSP golden references are documented in
`golden/README.md`. Configuration/OBS fixtures remain separate work.

Run the layout check without fetching or building JUCE, codecs or network libraries:

```powershell
cmake -S tools/compat-dump -B build/compat-layout
cmake --build build/compat-layout --config Release
ctest --test-dir build/compat-layout -C Release --output-on-failure
```

The same `shm_v14_layout` test is registered in the main CMake test build.
`.github/workflows/compat-layout.yml` checks the fixture on Windows and Linux.
`hs-layout-dump` writes JSON to stdout; `hs-layout-dump --check <fixture>`
compares the current ABI with the saved fixture and returns nonzero on mismatch.

Keep the fixture as the migration baseline. Do not regenerate it to hide a
layout change: protocol v14 must remain compatible throughout the migration.
When porting `protocol.h`, compare every Rust field offset, size and alignment
with this fixture, including arrays and explicit padding.

## Released plug-in fixtures

`fixtures/plugins-1.0.10/provenance.json` records the SHA-256 and byte size of
`dist/HEARASIDE-Setup-1.0.10.exe` and its six VST3/VST2 binaries. The installer was
unpacked with portable Inno Unpacker 2.71.2, verified against the publisher's
release archive digest. The installer was not executed and the extracted
binaries remain in ignored `build/compat-release-1.0.10/`.

Each plug-in/format has six `.bin` states, corresponding decoded `.xml` files,
and a capture manifest. These are unmodified JUCE host containers: a VST3 XML
wrapper containing base64 `IComponent` data or a VST2 FXB bank containing a chunk.
Capture restored every saved file into a fresh instance of the released plug-in
and checked all component XML and host parameter values. See
`tools/plugin-host-test/README.md` for scenarios and capture commands.

VST3 `metadata.json` comes from Rust `hs-compat-dump` calling the actual factory
and connected component/controller. It includes raw 16-byte Windows TUIDs,
numeric parameter IDs, order, defaults, flags and display text. The shipped
`moduleinfo.json` is also preserved without rewriting it. Track/Hub/App Audio
expose 10/8/9 VST3 parameters, including one host bypass parameter each. VST2
uses parameter indexes; its actual unique IDs are in the state manifests.
SDK plain-value conversions can return normalized values in JUCE, so use the
captured display text and minimum/maximum state XML for physical units.

Capture isolated bus/account/settings and disabled tunnels. Hub tokens were
freshly generated by disposable capture instances; the friend token is synthetic.
Channel color is supplied by the host and is not serialized by these processors.

Run the offline checks from the repository root:

```powershell
python compat/check_fixtures.py
python -m unittest discover -s compat -p test_fixtures.py
python compat/check_fixtures.py --release-root build/compat-release-1.0.10 --installer dist/HEARASIDE-Setup-1.0.10.exe
```

These checks decode the binary state, compare all 36 XML pairs, cross-check
VST3 native metadata with host parameters and shipped class IDs, and optionally
verify original artifact hashes. They run in CTest and the compatibility workflow
without loading native code. They do not replace a live restore or DAW test.
